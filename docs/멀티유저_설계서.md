# 멀티유저 개조 설계서 (지인용, 초대제)

> 전제: 지인 3~10명, 무료, 초대제. 상용 SaaS 아님 (그건 기획서 §11).
> 작업량: 1~2세션. 이 문서대로 진행하면 됨 — 새 AI 세션에 이 문서를 먼저 읽힐 것.
> 예상 비용: 유저당 월 $4~5 (풀자동 기준). 5명 ≈ 월 $25.

---

## 1. 핵심 설계 결정

### 1.1 인증: Supabase Auth (매직링크)
- 비밀번호 없이 이메일 링크 로그인 — 지인용으로 가장 간단
- **초대제 구현**: 별도 초대 시스템 대신 `allowed_emails` 테이블 + 가입 시 체크 (§4)
- 기존 Basic Auth(middleware)는 제거하고 Supabase 세션 체크로 교체

### 1.2 데이터 분리: 개인 vs 공유 (원가 절약의 핵심)

| 구분 | 테이블 | 처리 |
|---|---|---|
| **공유** (유저 수와 무관, 종목 기준 캐시) | quotes, candles, financials, news, stocks_master, kis_tokens | user_id 없음. 그대로 유지 |
| **개인** | notes, analyses, rules, briefings, discoveries | `user_id` 컬럼 추가 |
| **재설계 필요** | stocks (현재 = 내 watchlist) | 아래 §1.3 |

### 1.3 stocks 테이블 재설계 (제일 중요한 변경)
현재 `stocks` = watchlist 그 자체인데, quotes/candles/financials/news가 전부 stocks.symbol을 FK로 참조함.
멀티유저에서 A가 삭제한 종목을 B가 보고 있으면 캐시가 날아가는 문제 발생.

**해법: 전역 종목 레지스트리 + 개인 watchlist 분리**

```
stocks      → 전역 종목 레지스트리로 의미 변경 (등록만 되고 삭제 안 함. FK 유지)
watchlists  → 신규: (user_id, stock_symbol, added_at) — 개인 관심목록
```

- 종목 추가: stocks에 upsert(전역) + watchlists에 insert(개인)
- 종목 제거: watchlists에서만 delete (stocks와 캐시는 유지 — 다른 유저가 쓸 수 있음)

## 2. 스키마 변경 SQL

```sql
-- 개인 watchlist 분리
CREATE TABLE IF NOT EXISTS watchlists (
  user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  stock_symbol text NOT NULL REFERENCES stocks(symbol),
  added_at timestamp DEFAULT now() NOT NULL,
  PRIMARY KEY (user_id, stock_symbol)
);

-- 개인 테이블에 user_id 추가
ALTER TABLE notes       ADD COLUMN IF NOT EXISTS user_id uuid REFERENCES auth.users(id) ON DELETE CASCADE;
ALTER TABLE analyses    ADD COLUMN IF NOT EXISTS user_id uuid REFERENCES auth.users(id) ON DELETE CASCADE;
ALTER TABLE rules       ADD COLUMN IF NOT EXISTS user_id uuid REFERENCES auth.users(id) ON DELETE CASCADE;
ALTER TABLE briefings   ADD COLUMN IF NOT EXISTS user_id uuid REFERENCES auth.users(id) ON DELETE CASCADE;
ALTER TABLE discoveries ADD COLUMN IF NOT EXISTS user_id uuid REFERENCES auth.users(id) ON DELETE CASCADE;

-- 초대 화이트리스트
CREATE TABLE IF NOT EXISTS allowed_emails (
  email text PRIMARY KEY,
  invited_by text,
  created_at timestamp DEFAULT now() NOT NULL
);

-- 기존 내 데이터 백필 (본인 가입 후, auth.users에서 내 id 확인해서)
-- UPDATE notes SET user_id = '내-uuid' WHERE user_id IS NULL;  (analyses, rules, briefings, discoveries 동일)
-- INSERT INTO watchlists (user_id, stock_symbol) SELECT '내-uuid', symbol FROM stocks;

-- 백필 후 NOT NULL 강제
-- ALTER TABLE notes ALTER COLUMN user_id SET NOT NULL;  (나머지 동일)
```

### RLS (Row Level Security) — Supabase 콘솔 또는 SQL
> 우리 서버는 service role로 접근하므로 RLS가 필수는 아니지만, anon 키 노출 대비 안전장치로 권장.

```sql
ALTER TABLE notes ENABLE ROW LEVEL SECURITY;
CREATE POLICY notes_own ON notes FOR ALL
  USING (user_id = auth.uid()) WITH CHECK (user_id = auth.uid());
-- watchlists, analyses, rules, briefings, discoveries 동일 패턴
-- 공유 테이블(quotes 등)은 SELECT만 허용하는 read-only 정책
```

## 3. 코드 수정 지점 (파일별)

### 3.1 패키지
```bash
pnpm add @supabase/supabase-js @supabase/ssr
```
env 추가: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` (Supabase 대시보드 → Settings → API)

### 3.2 인증 레이어 (신규)
- `src/lib/supabase/server.ts` — 서버용 클라이언트 (@supabase/ssr 쿠키 연동)
- `src/lib/auth.ts` — `getUserId()`: 세션에서 uuid 반환, 없으면 redirect("/login")
- `src/app/login/page.tsx` — 이메일 입력 → 매직링크 발송. **발송 전 allowed_emails 체크** (없으면 "초대된 이메일이 아닙니다")
- `src/app/auth/callback/route.ts` — 매직링크 랜딩, 세션 교환
- `src/middleware.ts` — Basic Auth 제거 → Supabase 세션 갱신(@supabase/ssr updateSession 패턴) + 미로그인 시 /login 리다이렉트 (예외: /login, /auth, /api/cron)

### 3.3 쿼리 레이어 (§11.4 대비 덕분에 여기가 거의 전부)
| 파일 | 변경 |
|---|---|
| `queries/stocks.ts` | getWatchlist(userId), insertStock→stocks upsert + watchlists insert, deleteStock→watchlists만 delete |
| `queries/notes.ts` | 모든 함수에 userId 파라미터 + where(eq(notes.userId, userId)) |
| `queries/rules.ts` | 동일 + 시드도 유저별 (신규 유저 첫 접속 시 기본 룰 2개) |
| `queries/analyses.ts` | 동일 (latestVerdicts도 userId 필터) |
| `queries/briefings.ts`, `queries/discoveries.ts` | 동일 |
| `cache.ts` (quotes/fund/news/candles) | **변경 없음** (공유) |

### 3.4 호출부
- `app/actions.ts` — 각 액션 첫 줄에 `const userId = await getUserId()` 추가 후 쿼리에 전달
- 각 페이지(대시보드, 상세, 노트, 브리핑, 발굴, 설정, 전체종목) — 동일하게 userId 전달
- `api/analyze`, `api/review-note`, `api/note-to-rule`, `api/discover`, `api/briefing` — 세션에서 userId 추출 (없으면 401)

### 3.5 cron (유저별 루프)
`api/cron/briefing/route.ts`:
```ts
const users = await db.execute(sql`SELECT DISTINCT user_id FROM watchlists`);
for (const u of users) {
  await generateBriefing(slot, u.user_id).catch(log);   // 유저별 노트·watchlist·분석으로
  await generateDiscovery(u.user_id).catch(log);
}
```
`briefing-run.ts`, `discover-run.ts`에 userId 파라미터 추가.
⚠️ 유저 5명 × (브리핑+발굴) ≈ 3~5분 — Vercel maxDuration 300 안에 순차로 빠듯할 수 있음.
넘치면: 발굴은 아침만, 또는 유저별로 cron 시간 분산.

### 3.6 지인 온보딩 UX (선택이지만 추천)
- 신규 유저 빈 상태: 기존 스타터 칩 + "기본 룰 자동 생성" 이미 있음 → 그대로 동작
- 노트 0개 문제(콜드 스타트): "예시 노트 3개 복사해오기" 버튼 (기획서 §11.3의 스타터팩 축소판)

## 6. 주의사항 재확인
- KIS 앱키 = 내 계좌 키. 시세 조회 전용이지만 약관상 개인 이용 목적임을 인지할 것
- 지인 소수·무료·초대제 = 유사투자자문업 리스크 낮음. **공개 가입으로 전환하는 순간 기획서 §11.2 필수 검토**
- Anthropic 비용은 유저 수 비례 — Console Usage에서 모니터링, 이상 사용 시 유저별 횟수 제한 추가 (analyses에 user_id 있으니 카운트 쿼리로 간단)
